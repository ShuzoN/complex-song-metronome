# 再生アーキテクチャ 再設計提案 — 全体再生とグループ再生の統一

> 対象：`index.html` の再生系（Transport / PlaybackService / PlaybackScheduler / VideoSync / VideoPadService）。
> 方針：**動画マスター＋メトロノーム追従**（＝グループ再生の閉ループ機構）へ一本化し、
> 全体再生とグループ再生を「同じ機構・違う区間」に揃える。現状のパッチ延長ではなく**イチから設計し直す**前提。

---

## 0. 背景 — なぜ作り直すか

これまでの改修で、全体再生を「頭出し共通化（`startAtHead`）＋各rep頭でのクローズドループ再アンカー」まで持ってきた。
しかし根本的に **2つの再生が別々の同期思想で組まれている**ため、パッチを重ねても完全にはフィットしない。

- **グループ再生**：動画を cue へ**シークし、実着地を検知して**刻む＝**閉ループ**（動画の実位置に合わせる）。
- **全体再生**：頭で1回合わせたあとは**時計予測で各拍を並べる**＝**開ループ**を出発点にしており、
  後付けで境界だけ閉ループ補正を足した状態。境界の間（rep内）は依然 BPM 自走。

この非対称と、入口経路の重複・状態の分散（後述の課題群）が、挙動のブレと保守の難しさを生んでいる。
**「動画が時間の基準、メトロノームはそれに追従する」という単一モデル**へ作り直すのが本提案。

## 1. 見つかった課題（Issue バックログ）

> それぞれ GitHub issue 化できる粒度で記述。`現状扱い` は今の `index.html` の状態、`再設計での扱い` は本提案での解消方針。

### I1. 全体再生とグループ再生で同期機構が別物
- **症状**：グループ再生は動画にピタッと合うが、全体再生は曲が進むとズレる。
- **原因**：閉ループ（seek＋着地検知）と開ループ（時計予測）の混在。
- **影響**：挙動が非対称で、ユーザーの体感がモードで変わる。仕様として説明しづらい。
- **再設計での扱い**：両者を「区間 [start,end] を seek＋follow」に統一。差は**区間だけ**。

### I2. 入口経路が3つに重複（fragile）
- **現状**：`VideoSync.startAtHead`（全体）/ `startAtCue`（グループ）/ `startAtIndex`（パッド）が、
  `jump` / `countIn` / `resume` などのフラグ差で微妙に分岐（`index.html` VideoSync）。
- **影響**：`pollCue` の分岐が増え、到達検知・補正・overshoot 前倒しの経路がケースごとに変わる。バグ温床。
- **再設計での扱い**：**単一の seek+arrival プリミティブ**へ統合。呼び分けは「狙う位置」と「区間境界」だけ。

### I3. rep内は BPM 自走（アンカー間ドリフト）
- **症状**：BPM が実テンポと少しでも違うと rep の中でジワっと泳ぎ、次のrep頭でスナップして戻る。
- **原因**：記録・アンカー粒度が **rep頭のみ**（`recording && e.bar===0` → `stampCue`、`index.html:1681`）。
  rep内の各拍は `nextTime += span`（BPM）で並ぶ。
- **影響**：rep が長い曲・テンポが揺れる曲で泳ぎ＋境界スナップが目立つ。
- **再設計での扱い**：**cue駆動テンポ**（rep区間を「次cueまでの実時間」で満たすよう拍間隔を決める。C4）。
  粒度は rep のまま（本人合意）でも、rep内ドリフトをほぼ消せる。

### I4. 動画クロックの粒度・ジッタが未モデル化
- **原因**：`VideoGateway.time()`（YouTube `getCurrentTime`）を生で読む。更新は粗く（実測で数百ms粒度になりうる）、
  ジッタもある。今の閉ループは**各rep頭で生読み**しているため、境界ごとに最大その粒度ぶんの誤差が乗りうる。
- **影響**：追従は合うが、境界の置き位置がわずかに暴れる可能性。
- **再設計での扱い**：**平滑化した動画クロック推定**（線形フィット／位相同期）を持ち、発音時刻はそこから算出。C1。

### I5. 開ループ予測が clock skew / バッファで壊れる
- **症状**：再生レート差やバッファリングがあると全体再生が累積ドリフト（シミュレーションで最大0.78s）。
- **現状扱い**：クローズドループ再アンカーで各境界0.02s台に収束（改善済み）。ただし境界間は依然 BPM。
- **再設計での扱い**：連続追従（毎スケジューリングで平滑動画クロックへ写像）で境界間も詰める。

### I6. レイテンシ補正が手調整の定数・記録と再生で非対称
- **現状**：`CUE_LATENCY=0.26`（再生時 cue から引く）/ `REC_LATENCY=0.24`（記録時 足し戻す）を耳合わせ（`index.html` VideoSync）。
- **影響**：デバイス・ブラウザで最適値が変わる。左右非対称で二重に効く場面がある。
- **再設計での扱い**：単一の補正モデルに集約。将来は**校正（測定）**で自動化する余地（C10）。

### I7. 記録（全体レック）がアンカーとフィードバックする
- **現状**：`setAnchor(... && !recording)` で録音中はアンカーを切る対応済み。だが「録音中は素で流す／再生時は追従」が
  機構として明示的に分かれていない（同じ経路にフラグで割り込む）。
- **再設計での扱い**：**Record モード**と **Play モード**を最初から別レーンとして設計。

### I8. seek 後のスタール／位置キャッシュに場当たり対応
- **現状**：`getCurrentTime` はシーク直後に旧位置を数フレーム返す → `pollCue` の `seeked` 判定＋200ms猶予＋from近傍で回避。
- **影響**：ヒューリスティックで、状態遷移（BUFFERING→PLAYING）を素直に使えていない。
- **再設計での扱い**：**到達プリミティブ**（seek→バッファ→指定位置で再生開始、を状態遷移で確定）を1箇所に。

### I9. preroll（空白）の意味が限定的で分かりにくい
- **現状**：`wait = (mode==="all" && !skipWait) ? readPreroll() : 0`。全体再生かつ動画なしのときだけ効く。
- **影響**：動画同期時は無効。ユーザーモデルが「全体再生のときだけ」で例外的。
- **再設計での扱い**：**音のみモード専用のカウントイン**として明確化（S5）。

### I10. スケジューラが動画を読み始め、責務境界が崩れつつある
- **現状**：本来「発音時刻は bpm から都度計算、DOM/動画由来は含めない」だった `PlaybackScheduler` に、
  動画実位置を読む関数を注入（`setAnchor(fn)`）。実用上は動くが、層の純粋性が薄れている。
- **再設計での扱い**：**Clock 抽象**を1枚かませ、スケジューラは「Clock から現在位置を引く」だけにする。

### I11. count-in（助走）が動画同期時のみの特殊ケース
- **現状**：`countInFor` で前グループ末尾1〜2小節を downbeat 手前に鳴らす（動画同期のグループ再生時）。
- **影響**：モード×フラグの組合せが増える一因。
- **再設計での扱い**：区間開始の共通オプション「lead-in（前区間の尻を鳴らす）」として一般化。

### I12. 「現在の曲位置」の単一ソースがない
- **現状**：UI ハイライトは `PlaybackScheduler.queue`／`Transport.cur` 由来、同期は動画由来。両者が別経路。
- **影響**：表示と実同期がわずかにズレうる。全画面ストリップ・タイムラインの一貫性も別計算。
- **再設計での扱い**：**単一の position source**（Transport が公開する `songPosition()`）から UI も同期も駆動。

## 2. 目標仕様（Spec）

### 用語
- **区間 (segment)**：再生する範囲 `[startIndex, endIndex)`（timeline 上の拍インデックス）。
- **cue**：ある rep 頭の**動画タイムコード**（記録値。`repCues[rep]`、rep0 は `g.cue`）。
- **follow（追従）**：動画は連続再生したまま、メトロノームの発音時刻を動画実位置へ合わせ続けること。
- **master clock**：時間の基準。動画同期時は動画、音のみ時はメトロノーム（AudioContext）。

### 音の連続性の原則（最重要インバリアント）
- **追従中に動画を seek しない。** 動画の音声は途切れさせない。
- 動画を seek するのは **区間の開始（頭出し）とユーザーの明示シーク（±5秒/一時停止復帰）** のみ。
- 追従で動くのは**メトロノーム（離散クリック）だけ**。微調整で「ごく短い空き」や「わずかな前倒し（近接打）」は許容。

### 再生モードの統一仕様
| モード | 区間 | 動画 | 追従 |
|---|---|---|---|
| **全体再生** | `[曲頭, 曲末]` | 曲頭cue（無ければ0）へ seek → 連続再生 | あり（動画同期時） |
| **グループ再生** | `[グループ頭, グループ末]`※ | グループ頭cueへ seek → 連続再生 | あり |
| **パッド ±5s / 再開** | 現在位置 ± Δ から | 相対 seek → 連続再生 | あり |
| **音のみ（動画なし）** | 各モードの区間 | — | なし（メトロノームが master・BPM） |
| **全体レック（記録）** | `[曲頭, 曲末]` | 動画0から連続再生 | **なし（素で流して cue を記録）** |

※ グループ再生の区間終わりの扱いは **未決事項 D1**（止める／全体へ流す）。

### フォールバック
- **cue 未記録**：追従先が無い → 動画は0から流し、メトロノームは BPM 自走（ベストエフォート）。全体レックを促す。
- **動画読めない/応答なし**：メトロノーム単体で開始（現行の退避と同じ）。

## 3. 提案アーキテクチャ

```
 UI (PlaybarView / FullscreenView / GroupView / Space)
        │  play(segment) / stop() / seekBy() / togglePause()
        ▼
 Transport（再生ステートマシン：区間・モード・record/play）
   │        │                         ▲ songPosition()（UIも同期もここから）
   │        ▼                         │
   │   Follower Scheduler ────────────┘   … Clock から現在位置を引き、各拍の発音時刻を算出
   │        │  click(time)
   │        ▼
   │   SoundGateway（Web Audio）
   │
   ├── Timeline（位置マップ：拍 ↔ 曲位置/動画位置。cue とテンポで写像）
   │
   └── Clock 抽象
         ├─ VideoClock … 平滑化した動画位置推定＋seek/play/pause（master：動画同期時）
         └─ AudioClock … AudioContext 時刻→曲位置（master：音のみ時）
```

### 3.1 Timeline（位置マップ）
拍の平坦リスト。各拍が持つ：`gid/rep/bar/beat`・`meter`・`accent`・`gbpm`・
`songPos`（基準テンポでの累積秒）・`vt`（動画タイムコード写像）・`anchor`（この拍が cue を持つか）。
- rep 頭にだけ `anchor=cue`（粒度は rep 固定）。
- **cue駆動テンポ（C4）**：各 anchored rep について「次の anchored cue までの実時間」を、
  その区間の拍へ**音価比で配分**して `vt` を作る。→ アンカー間も動画実時間に沿う。
- 末尾 rep や cue 欠落区間は BPM/gbpm で補間。

### 3.2 Clock 抽象（キモ）
`Clock` は「今この瞬間、曲は動画タイムコードのどこにいるか」を**滑らかに**返す。
- **VideoClock**：`getCurrentTime` の生読みを**線形モデル `v(t)=rate·t+offset` に位相同期**（低ゲインで更新）。
  生読みのジッタ・粗さを吸収し、`positionAt(audioTime)` を連続値で返す。seek/play/pause も担う。
- **AudioClock**：`songPos = (audioTime − t0)` を BPM で拍に写す（音のみモード）。
- スケジューラは Clock を通してのみ時間を知る → **I10（層の純粋性）を回復**。

### 3.3 Follower Scheduler
先読み（~0.1s）で各拍を予約するが、発音時刻は**都度 Clock から算出**：
```
targetAudioTime(beat) = audioNow + ( compensate(beat.vt) − videoClock.positionNow() )
```
- 動画同期時：平滑動画クロックへ写像 → 連続追従（rep内も詰まる）。
- 音のみ時：AudioClock の等間隔（従来どおり）。
- 過去への予約は `max(target, now+ε)` でガード（近接打は許容）。

### 3.4 単一 seek+arrival プリミティブ
`seekAndPlay(videoTime, {lead})`：
1. `seekTo(videoTime − lead)`（手前に置く）→ `play()`
2. 状態遷移（UNSTARTED/BUFFERING→PLAYING）と位置で**実到達を確定**（`pollCue` のヒューリスティックを1本化）
3. 到達したら VideoClock を初期化（位相同期の初期値）→ follow 開始
- 全体/グループ/パッドは、渡す `videoTime` と区間が違うだけ。**I2/I8 を解消**。

### 3.5 Record / Play レーン分離
- **Record**：動画0から連続再生、メトロノームは BPM 自走（follow しない）、各 rep 頭で `getCurrentTime` を記録。
- **Play**：Timeline の cue で follow。
- 「同じ経路に `!recording` フラグ」ではなく最初から別レーンにして **I7 を構造で解消**。

### 3.6 統一戦略（グループ再生機構の一般化）★

**核の抽出**：グループ再生 ＝ `seek → 着地検知(pollCue) → 実位置へ downbeat をピン`。
再利用したいのは **着地検知＋ピン（閉ループ）**。`seek` は「そこへジャンプする」ためだけのもの。

**全体再生への翻訳**：

> **頭で1回だけ seek。以降は seek せず、動画が各グループの cue を“通過するのを待って”、
> そのグループの downbeat をピンし直す。** ＝ グループ再生のピンを**連鎖**させる。区間が `[曲頭,曲末]` になっただけ。

これで「動画を seek で切らない（音の連続性）」を**構造的に**満たす（前グループの再生が自然にそこまで運ぶ）。

**1点だけ本質的な翻訳**：Web Audio は発音を**先に予約**する必要があり「着地して即発音」は原理的に不可
（＝素朴な連鎖だと境界スナップが出る）。そこで：
- **先読み予約は「平滑動画クロック」から**：`getCurrentTime` を `v(t)=rate·t+offset` に低ゲイン位相同期し、
  各拍を `audioNow + (compensate(cue) − 動画位置)` で少し先に予約。
- **着地検知は「ピンの補正」に格下げ**：各境界で観測した実位置で offset を軽く引き直す
  （＝グループ再生の overshoot 前倒しの連続版）。

**ピンの間（rep内）を詰める**：**cue駆動テンポ**（rep区間 `[cue_n, cue_{n+1}]` の実時間を音価比で配分）で、
rep 粒度のままアンカー間も動画実時間に沿わせる。末尾rep・cue欠落は BPM/gbpm へフォールバック。

**プリミティブの統合**：
```
SyncPoint       = { songBeatIndex, cue }                 // cue↔downbeat（rep頭）
seekAndArrive(cue, lead)                                  // seek→着地検知→クロック初期化（頭/グループ/±5秒 共通）
observePin(cue)                                           // 着地の連続版：観測して平滑クロックの offset を補正
clockForBeat(beat) = smoothedVideoClock.map(beat.vt)     // 先読み予約の時刻源
```
- **全体再生** ＝ `seekAndArrive(headCue)` → 区間 `[曲頭,曲末]`、各境界で `observePin(cue_n)`
- **グループ再生** ＝ `seekAndArrive(cueG)` → 区間 `[G頭, G末]`
- **パッド ±5s** ＝ `seekAndArrive(nowVideo ± Δ)`
→ `startAtHead/startAtCue/startAtIndex` が **seekAndArrive 1本**に畳める（I2 解消）。

**ソフト要件との対応**：
| 全体再生のソフト要件 | 満たし方 |
|---|---|
| 曲を通しで連続再生 | ピンを連鎖（区間 `[曲頭,曲末]`） |
| 動画にずっと同期 | 各境界で観測ピン＋間は cue駆動テンポ |
| 動画の音を切らない | seek は頭で1回だけ（境界は観測のみ） |
| 普通のプレイヤー挙動 | 押す→頭出し→通し。停止/一時停止/±5秒も同じ seek+着地 |
| グループ再生と仕様統一 | 同じ核（SyncPoint＋着地/観測）を共有、差は区間だけ |

## 4. 主要な技術課題（Challenges）

- **C1. 動画クロックの平滑化（最重要）**：`getCurrentTime` の粗さ・ジッタを、位相同期（PLL的）な `v(t)=rate·t+offset` で吸収。
  ゲインが高いとジッタが乗り、低いと追従が遅い → チューニングが要る。seek 直後の再初期化も設計対象。
- **C2. 二重 master clock の切替**：動画あり=VideoClock、なし=AudioClock。切替時の状態リセットを明確に。
- **C3. cue駆動テンポの配分方法**：rep区間の実時間を拍へ配分する重み（一律 or 音価比）。境界での不連続を避ける。
- **C4. gbpm / 可変BPM との整合**：cue があればテンポは cue が主、無ければ gbpm/基準 BPM。優先順位を仕様化。
- **C5. レイテンシ補正の一元化・校正**：`CUE_LATENCY`/`REC_LATENCY` を単一モデルへ。将来は測定で自動校正（クリックと動画音の位相を合わせる）。
- **C6. 到達検知の堅牢化**：状態遷移＋位置＋タイムアウトで「確実に着いた」を判定。stall/キャッシュ/応答なしを1箇所で。
- **C7. UI 駆動の一本化**：`songPosition()` からハイライト・全画面ストリップ・タイムラインを描く（I12）。
- **C8. count-in / preroll の一般化**：区間開始オプション（前区間の尻を鳴らす lead-in／音のみの空白）として整理（I9/I11）。
- **C9. stop/pause/resume**：動画マスターの一時停止＝メトロノームも停止／現在位置から follow 再開、を統一。
- **C10. テスト容易性**：Clock/Gateway を抽象化し、**時計を差し替えてユニットテスト**できるようにする（今回のドリフト検証もコードで再現できた）。

---

## 5. 移行方針（フルリライト前提だが段階可能）

1. **Clock/Timeline を先に切り出す**（純粋・テスト可能）。既存の `PlaybackService`/`Domain` から写像ロジックを移す。
2. **Follower Scheduler** を Clock 越しに実装し、まず音のみモードで既存同等を担保。
3. **seek+arrival プリミティブ**へ VideoSync の3経路を統合。
4. **VideoClock 平滑化**を入れ、動画同期の follow を全体/グループ共通で通す。
5. **Record レーン**を分離。UI 駆動を `songPosition()` に一本化。
6. 旧 `Transport/PlaybackScheduler/VideoSync/VideoPadService` を段階的に置換。

> 各段でヘッドレス起動＋（時計スタブでの）ユニットテストを回し、実機（YouTube）で耳合わせ。

- **D2. cue駆動テンポを採用するか**：rep区間を cue間隔で満たす（I3/I5 に効く）か、BPM 主のままか。
- **D3. レイテンシ校正 UI**：手調整の定数のままか、測定ベースの校正を入れるか（C5/C10）。
- **D4. 記録粒度**：rep 固定（今回合意）。将来 bar 粒度へ拡張する余地は Timeline 設計に残すか。
- **D5. 音のみモードの follow**：動画が無いとき tap-tempo 等で「実演に合わせる」入口を用意するか（範囲外候補）。
